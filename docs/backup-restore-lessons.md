# 备份恢复、目录迁移与项目拆分经验

本文记录本次恢复旧机器项目时可复用的方法。具体恢复结果与当前部署说明分开：备份快照、当次恢复验证和当前运行状态不是同一个概念。

## 1. 先找备份入口与当前清单

本次备份入口为 `/mnt/waylens-genai-shanghai-backup/lingzhang`。先读最新指针、README、BACKUP_INDEX 和实际引用的 manifest，再选择 payload。

疲劳检测独立备份的最新索引引用了 revisions 下的 CURRENT_FILES；直接读原始 metadata 文件会得到旧命名空间。旧增量可能已经被新的完整备份替代，不能把所有包按名字随意叠加。

可复用顺序：

1. 确认最新快照与增量的覆盖关系。
2. 根据当前索引解析 manifest 路径，不猜文件位置。
3. 核对磁盘空间、工具和恢复根目录是否为空。
4. 从 manifest 选择需要的文件/pool，明确公开数据集的排除范围。
5. 按依赖顺序恢复，校验分片与文件 SHA256。
6. 恢复后核对文件数量、大小、链接、Git 和数据库。

原始共享 tar 分片可能同时包含多类历史内容，应按当前 manifest 选择输出成员。跳过公开数据不等于直接删除包含混合内容的历史分片。

## 2. 目录名不等于恢复了整个项目

本次疲劳检测备份包含碰撞检测目录下约 5.7 MB 的 V-JEPA2 代码依赖。恢复时出现相邻项目名称，首先检查实际文件和代码引用，不单凭目录名认定恢复了完整无关项目。

后来将 V-JEPA2 加入疲劳检测项目自身 `third_party/vjepa2` 子模块，并将运行代码改成仓库相对路径。迁移依赖时比较实际使用源码；本次 32 个上游 Python 文件与原恢复版本一致。

```bash
git submodule update --init --recursive
git submodule status
```

子模块 pin 记录源码版本，不等于模型权重也已恢复。缺少运行环境时，语法、路径和 Git 验证不能代替模型执行测试。

## 3. 软链接、实体目录与移动后的再验证

当前 `/home/lingzhang/workspace` 是指向 `/data/backup` 的软链接。操作前使用 resolve/readlink 确认真正的存储位置，不能把该目录当作可随意清理的临时 scratch。

恢复工具保留原 `mnt/nvme7/lingzhang/...` 层级，后来项目实体移到 workspace 根目录。移动时必须区分：

- 顶层项目快捷链接。
- 项目内部指向数据、模型、外部代码的链接。
- 代码、配置、数据库中写死的旧绝对路径。
- Git submodule 的相对 gitdir 引用。

先移动实体并验证新入口，再决定是否保留或删除旧路径。删除旧兼容软链接前，重新扫描仍指向旧路径的链接及配置；不能只确认顶层实体存在。恢复时通过的链接检查，不代表移动后仍然通过。

内部模型链接优先使用项目内相对路径；跨目录数据应集中配置。已明确跳过公开数据和可重建缓存时，将预期断链记录下来，与意外缺失区分。

## 4. 本机读取挂载备份时遇到的问题

- 系统没有 `python` 命令，使用已存在的 `python3`/`python3.12`，不要假设名称。
- shell 默认 Python 可能没有 pip/torch；先查看解释器与环境，而不是认定包彻底不存在。
- 恢复工作目录可写，不代表其父目录也可写。scratch 应选当前用户可写且容量足够的位置。
- 本次 zstd 通过文件名读取 scratch 中的软链接时忽略了该文件；改用实体副本或明确允许的读取方式，并检查退出码。不能仅因输出为空就认定 manifest 为空。
- 多分片 zstd/tar 是连续流，不能把任意一个分片独立当 tar 解压。
- 同一归档流不能随意从中间恢复。只复用明确完成并验证的 pool，未完成部分从清单重新提取。

独立 pool 可以并行恢复，但需要避免输出路径冲突，并在所有文件完成后恢复链接与最终目录权限。本次分片先复制到本地 scratch，再校验和解压，减少了挂载存储的重复远程读取。

## 5. Codex 会话恢复要合并，不覆盖

原备份的会话文件有普通 JSONL 和压缩 JSONL。恢复时读取会话数据库索引，解压缺少的正文；索引路径直接以 `.jsonl.zst` 结尾的记录也要处理。

当前 `.codex` 已有正在进行的会话，不应直接用旧 `state_5.sqlite` 覆盖它。可复用方法：

1. 用 SQLite backup API 保存当前数据库的一致性副本，不能只复制活动库主文件而忽略 WAL。
2. 在独立目录恢复完整历史层与增量，检查 quick_check。
3. 验证每条索引对应的 rollout 正文存在且首行 JSON 可解析。
4. 将旧路径重定位到新项目，按会话 ID 合并，保留现有会话。
5. 在相应锁下补全 JSONL 会话索引，处理关联历史数据库。
6. 如要求脱离恢复目录使用，复制为当前 `.codex` 的实体文件，逐文件校验后原子替换链接。

本次合并了 111 个历史会话并保留当时的当前会话；496 个会话/附件相关文件最终复制为实体文件。数字是当次记录，不应作为后续清理条件。

## 6. 拆项目以可独立部署为验收条件

本次将旧 asr-tts 拆为：

- ai-gateway：账号、鉴权、额度、代理、Worker/D1 与公网入口。
- model-serving：模型源码、模型配置、权重目录、独立环境和模型进程。

不仅复制文件，还需要检查运行时 import、启动脚本、服务凭据、模型链接、上游 URL、测试分组与部署文档。模型启动器不能依赖网关虚拟环境，也不能顺手启动账号服务或公网隧道。

旧目录删除前：确认新项目没有指向旧目录的符号链接/运行路径，核对账号库数量与完整性，再删除。若今后还要删除其他快照，同样重新检查，不能沿用旧结论。

## 7. 验证结果应写清边界

| 检查 | 适用目标 |
|---|---|
| 分片与文件 SHA256 | 备份内容正确 |
| manifest 数量、大小与链接核对 | 命名空间完整，排除项可解释 |
| SQLite quick_check / foreign_key_check | 数据库可读及关联一致 |
| Git connectivity / submodule status | 仓库与固定依赖可用 |
| CPU 侧协议和部署脚本测试 | 路由、准入、配置与缺失资源提示 |
| 真实 GPU 推理 | 环境、权重、设备与模型执行正确 |

原备份省略了部分公开模型权重、虚拟环境和可重建特征缓存。因此不能把“源码恢复完成”写成“服务已就绪”。具体模型恢复清单在 model-serving 项目，当前账号部署状态见 [Worker/D1 文档](cloudflare.md)。
